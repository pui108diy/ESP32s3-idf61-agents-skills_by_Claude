# PROTOCOL.md — กติกาของ skill esp32s3-idf61

> เวอร์ชัน v0.10-draft · ใช้กับ ESP32-S3 + ESP-IDF v6.1
> ส่วน A: กติกาสำหรับ agent ที่ใช้ skill เขียนโค้ด
> ส่วน B: กติกาสำหรับคนและ AI ที่ช่วยกันสร้าง/แก้ไฟล์ของ skill

## ส่วน A — กติกาตอนเขียนโค้ด (runtime)

### A.1 ลำดับแหล่งความจริง (สูง → ต่ำ)
1. header/ซอร์สของ ESP-IDF v6.1 ใน RAG ([H61] [C61])
2. `soc_caps.h` และไฟล์ใน `soc/esp32s3` ([SOC])
3. test_apps ของ IDF ([T61]), migration guide ([MIG])
4. TRM, Datasheet ([TRM] [DS])
5. reference ของ skill นี้ที่ติดป้ายแล้ว
6. เว็บ ([WEB]) ระบุลิงก์ทุกครั้ง
7. ความรู้ทั่วไป ([GEN]) ใช้เป็นข้อมูลประกอบเท่านั้น ห้ามใช้ตัดสิน signature/ค่าคงที่

เมื่อแหล่งขัดกัน ยึดลำดับบน และแจ้งความขัดแย้งให้ผู้ใช้ทราบ

### A.3 กติกาการตอบ
- ทุกประโยคที่เป็นข้อเท็จจริงของ API/ฮาร์ดแวร์ ต้องมีป้ายท้ายประโยค
- ถ้าข้อมูลที่ต้องใช้เป็น [UNV] หรือไม่มีใน reference: บอกผู้ใช้ตรงๆ แล้วเสนอ 2 ทาง คือขอให้ผู้ใช้เพิ่มไฟล์ header เข้า RAG หรือค้นเว็บ (ติดป้าย [WEB])
- ห้ามเดา signature, ชื่อฟังก์ชัน, ชื่อ macro หรือค่า default
- ทุกตัวอย่างโค้ดต้องระบุสถานะ: [BUILD] ผ่าน / ยังไม่ build และ [HW] ผ่าน / ยังไม่ทดสอบ
- ทุกจุดที่ต่างระหว่างเวอร์ชัน ต้องติด marker (v5.x / v6.0 / v6.1)
- โค้ดที่ขึ้นกับ capability ของชิป ต้องครอบด้วย `#if SOC_*` ตาม capability matrix

### A.4 Gate ก่อนส่งโค้ด (เช็คตามลำดับ)
1. ระบุงานตรงกับ reference ไหน (SKILL.md ตาราง Dependency Map) และโหลดครบ
2. โหลด Hot-List ของกลุ่มนั้น และเทียบโค้ดกับทุกรหัสที่เกี่ยวข้อง
3. ทุก include และ component อยู่ใน `PRIV_REQUIRES`/`REQUIRES` (มี CMakeLists ให้เสมอเมื่อสร้างโปรเจกต์)
4. ทุก API ที่ใช้อยู่ใน reference ที่ติดป้าย (หรือถ้าไม่อยู่ ให้ตรวจจากแหล่งตาม A.1)
5. ขา GPIO ที่เลือก ไม่ชนข้อห้าม (flash/PSRAM, strapping, USB/JTAG/UART0)
6. แนบรายการ "ที่ยังไม่ได้ตรวจ" ถ้ามี

### A.5 ระดับความร้ายแรงของกับดัก (tag ใน Hot-List)

| tag | นิยาม | ตัวอย่าง | วิธีจับ |
|---|---|---|---|
| [COMPILE] | build ไม่ผ่าน (error หรือ warning ที่ถือเป็น error) | signature/ชนิดผิด, macro/ฟังก์ชันถูกลบ, ฟิลด์ struct ไม่มีบนชิปนี้ | `idf.py build` |
| [RUNTIME] | build ผ่าน แต่ทำงานผิดแบบสังเกตได้ (error code, abort, panic, ค้าง) | `ESP_ERROR_CHECK` abort, ใช้ขาที่ไม่มี, เรียกผิดลำดับ | รันและดู log |
| [SILENT] | build ผ่าน รันได้ ไม่มี error แต่ผลผิด/ไม่เสถียร | ใช้ `1UL` แทน `1ULL`, ลืม `BIT()`, ลำดับ hold/unhold ทำให้ระดับขากระโดด | ต้องมีการทดสอบ/วัด หรือรีวิวโดยรหัส |

ลำดับความสำคัญตอนรีวิว: SILENT > RUNTIME > COMPILE (เพราะ SILENT ตรวจพบยากที่สุด)

## ส่วน B — กติกาการสร้างและแก้ไฟล์ของ skill

### B.1 สภาพแวดล้อมการทำงาน (สำคัญ)
- ที่นี่ไม่ใช่สภาพแวดล้อมที่ AI รันคำสั่ง/แก้ไฟล์ได้เอง ทุกไฟล์ที่ AI สร้างจะถูกพิมพ์ในแชท แล้วมนุษย์คัดลอกไปวาง
- สิ้นสุดแต่ละ session มนุษย์รวมไฟล์ที่แก้แล้วอัปโหลดเข้า RAG
- ดังนั้น AI ต้องออกเอกสารให้ "คัดลอกไปวางได้โดยไม่ต้องค้นหาเอง"
- AI รัน build ไม่ได้ ผลทดสอบ [BUILD] และ [HW] มาจากมนุษย์เท่านั้น
- ตัวอ่านไฟล์แนบและ RAG ไม่ได้ส่งไฟล์ทั้งก้อนให้ AI แต่ดึงเฉพาะส่วนที่ตรงกับคำถามที่ AI ส่งไป ผลจึงขึ้นกับคำถาม: ตอนอ่านไฟล์ผลรัน AI ต้องสั่ง "คัดลอกตรงตัวอักษร ไม่สรุป" และขอแยกตามหัว `### Xn` ข้อสรุปแบบ "ไม่มี" ที่ได้จากข้อความสรุปห้ามใช้ปิดข้อ [UNV]
- แชทและ RAG ของผู้ใช้รับไฟล์ `.txt` และ `.docx` เท่านั้น ไฟล์ `.md` ที่จะอัปโหลดให้ผู้ใช้คัดลอกเป็นนามสกุล `.txt` (หรือ `.docx`) โดยเก็บ `.md` เป็นต้นฉบับ
- RAG รับเป็นไฟล์เดี่ยว ไม่รับไดเรกทอรี และมีจำกัดจำนวนไฟล์: โปรเจกต์ตัวอย่างต้องเก็บเป็น `labs/<project>.md` ไฟล์เดียว (วิธีสร้าง วิธีรัน ผลที่คาด สถานะทดสอบ และซอร์สทุกไฟล์เป็น fenced code)

### B.2 โครงสร้างไฟล์ของ skill

```text
skills/esp32s3-idf61/
├── SKILL.md              Router
├── PROTOCOL.md           ไฟล์นี้
├── CHANGELOG.md          ประวัติการเปลี่ยนแปลงและเหตุผล
├── HANDOFF.md            ส่งต่อ session (เขียนทับทุกครั้ง)
├── references/peripherals/<api>.md
├── hotlist/<GROUP>.md    หนึ่งไฟล์ต่อกลุ่ม API
├── evidence/<api>-evidence.md  ข้อความต้นฉบับ (verbatim) ที่ใช้ยืนยัน เก็บไว้เมื่อไฟล์ต้นทางถูกถอดจาก RAG
├── tools/verify_<api>_unv[N].sh  สคริปต์ grep ปิดข้อ [UNV] บนเครื่องผู้ใช้ (อ่านอย่างเดียว)
├── tools/verify_<api>_unv[N].sh_verify[N].log_.md   ผลรันที่ผู้ใช้บันทึก (เก็บเป็นหลักฐาน [VER])
├── labs/<project>.md           วิธีสร้าง วิธีรัน ผลที่คาด สถานะทดสอบ และซอร์สทั้งหมดของโปรเจกต์ (ไฟล์เดียว)
├── snippets/ หรือ labs/  โปรเจกต์ที่ build ได้จริง
└── index/                (แผน) api-index.tsv, removed-renamed.md, soc-caps-s3.md
```

### B.3 Template ของ reference file
1. หัวไฟล์: เวอร์ชัน, สถานะ (DRAFT / RC / FINAL), เป้าหมาย, ตารางป้าย
2. §0 TL;DR (ข้อที่ตรวจแล้วเท่านั้น)
3. §1 Include และ CMake
4. §2 ข้อเท็จจริงฮาร์ดแวร์ของ S3
5. §3 Capability matrix (ค่า SOC_* + ผลต่อโค้ด)
6. §4 Types, §5 API, §6 เรื่องเฉพาะของ API นั้น
7. ดัชนี Hot-List (รหัส ↔ หัวข้อ)
8. ตัวอย่างและสถานะทดสอบ
9. ที่ยังไม่ยืนยัน
10. บันทึกการตรวจ

กฎ:
- โค้ดทุกก้อนอยู่ใน fenced code block พร้อมภาษา
- ไม่พิมพ์ตัวเลขสรุป (จำนวนข้อ, จำนวนไฟล์) ด้วยมือ ให้นับจากไฟล์จริงตอนออกเวอร์ชัน (B.8)
- สถานะ FINAL ได้เมื่อไม่มี [UNV] ที่เกี่ยวกับ signature/ค่า/พฤติกรรมที่โค้ดใช้ และตัวอย่างหลัก [BUILD] ผ่าน

### B.4 ขั้นตอนผูก Hot-List กับ reference (ผูกสองทาง)

**รูปแบบ entry ใน `hotlist/<GROUP>.md`:**

```markdown
### GPIO-05 [RUNTIME]
- **ผิด:** ...
- **ถูก:** ...
- **หลักฐาน:** [H61] ...
- **ref:** gpio.md §7.4 · **verified-in:** v6.1 · **[HW]:** รอ T4
```

**ขั้นตอนเพิ่มกับดักใหม่:**
1. หาหลักฐานจาก header/ซอร์ส ตาม A.1 (ห้ามเขียนจากความจำ)
2. กำหนด tag ตาม A.5
3. สร้าง entry ใน `hotlist/<GROUP>.md` ใช้รหัสถัดไปของกลุ่ม ถ้ายังไม่ทราบเลขล่าสุดให้ใช้ `<GROUP>-Pnn` ชั่วคราว
4. เพิ่มแถวในตาราง "ดัชนี Hot-List" ท้ายไฟล์ reference ที่ตรงกัน พร้อมหัวข้อที่อ้างถึง
5. ออกเป็น Edit Block (B.6) ให้ทั้งสองไฟล์ในครั้งเดียว
6. บันทึกใน CHANGELOG.md

**ผูกสองทาง:** ทุกรหัสที่ปรากฏใน reference ต้องมี entry ใน hotlist และทุก entry ใน hotlist ต้องถูกอ้างอย่างน้อยหนึ่งที่ใน reference

**นโยบายรหัส:**
- รหัสที่กำหนดเลขจริงแล้ว ห้ามเปลี่ยนเลข ห้ามนำเลขกลับมาใช้ซ้ำ
- entry ที่เลิกใช้ ให้ใส่ `RETIRED (เหตุผล, เวอร์ชัน)` แทนการลบ
- รหัส `-Pnn` เปลี่ยนเป็นเลขจริงได้ครั้งเดียว โดยบันทึกตาราง map ใน CHANGELOG.md

### B.5 ขั้นตอนตรวจกับแหล่งจริง (ก่อนใส่ป้าย [H61]/[C61]/[SOC])
1. ค้น RAG ด้วยชื่อ symbol/macro/ข้อความเฉพาะ
2. ยืนยัน signature จากบรรทัดประกาศจริง ไม่ใช่จากตัวอย่างหรือเอกสารเล่าเรื่อง
3. การยืนยันว่า "ไม่มี" (เช่น macro ไม่นิยาม) ต้องเห็นบล็อกที่เกี่ยวข้องต่อเนื่อง และให้ยืนยันซ้ำด้วยโปรแกรมตรวจ (เช่น caps_probe) เมื่อทำได้
4. ถ้าค้นแล้วไม่พบ: ติด [UNV] และเพิ่มในรายการ "ที่ยังไม่ยืนยัน" พร้อมระบุไฟล์ที่ต้องการให้เพิ่มเข้า RAG
5. เอกสารเล่าเรื่อง/ตัวอย่างของคนอื่น (รวม GLM) ติด [GLM] จนกว่าจะตรวจกับข้อ 1–2
6. ช่อง RAG จำกัดจำนวนไฟล์ ก่อนที่ผู้ใช้จะถอดไฟล์ต้นทางออก ต้องสร้างหรืออัปเดต `evidence/<api>-evidence.md` ให้ครอบคลุมทุกข้อที่ติดป้าย [H61] [C61] [SOC] [T61] ของ reference นั้น และระบุในไฟล์ว่ารายการใดดึงรอบไหน
7. ข้อที่ค้น RAG ไม่ได้แต่ผู้ใช้ปิดได้ด้วยคำสั่งบนเครื่อง ให้ออกสคริปต์ `tools/verify_<api>_unv.sh` (อ่านอย่างเดียว) แทนการรอไฟล์เพิ่ม
8. ค่า `CONFIG_SOC_*` ใน Kconfig/sdkconfig ห้ามใช้เป็นหลักฐานของ mask หรือ expression ใน `soc_caps.h` (ใช้ได้เฉพาะ bool/int ง่ายๆ)
9. สคริปต์ verify ห้ามตัดผลด้วย `head` หรือ `tail` เมื่อผลนั้นจะใช้ยืนยัน "ไม่มี" ให้บันทึกลงไฟล์เต็ม และผู้ใช้แนบเป็นไฟล์ ถ้า AI อ่านได้เพียงสรุป (ไม่ใช่ข้อความดิบ) ให้ติดคำเตือนในไฟล์ evidence และขอ raw เมื่อข้อสรุปมีผลต่อโค้ด
10. ผลที่ได้จาก grep ของชื่อสั้นอาจติดชื่อที่มี prefix (เช่น `esp_rom_gpio_pad_select_gpio` ติด pattern `gpio_pad_select_gpio`) ใช้ `grep -w` เมื่อต้องการชื่อเปล่า
11. ผลรัน verify บันทึกเป็นไฟล์เดียวชื่อ `verify_<api>_unv[N].sh_verify[N].log_.md` (เช่น `verify_gpio_unv2.sh_verify2.log_.md`) ผู้ใช้รันสคริปต์เองด้วย `bash verify_<api>_unv[N].sh > verify[N].log 2>&1` แล้วนำ "โค้ดที่รัน" และ "ผลที่ได้" มาใส่ในไฟล์นี้เอง ไม่ใช้สคริปต์ห่อ โครงไฟล์: (ก) สคริปต์ทั้งก้อนใน fenced block ภาษา bash (ข) ผลทั้งก้อนใน fenced block ภาษา text ไม่แก้ ไม่ตัด (ค) หัวสั้นบอกวันที่หรือเครื่องได้ถ้าต้องการ เหตุผลที่เก็บโค้ดคู่ผล: skill จะถูกเผยแพร่และ agent ตัวอื่นต้องอ่านแล้วรู้ว่าอะไรถูกพิสูจน์ ดังนั้นสคริปต์ต้องมี (1) คอมเมนต์หัวไฟล์บอกวัตถุประสงค์และวิธีใช้ (2) คอมเมนต์หรือบรรทัด `echo "### Xn ..."` บอกว่าแต่ละหัวข้อพิสูจน์ข้อไหน (3) บรรทัด `(จบ Xn)` บอกวิธีอ่านผล เช่น "ไม่มีบรรทัด = ไม่พบ" (4) ห้ามใส่ `2>/dev/null` กับคำสั่งที่ผลว่างเป็นหลักฐาน เพราะ path ผิดจะเงียบและดูเหมือน "ไม่พบ" ไฟล์นี้คือหลักฐานระดับ [VER] และสรุปเข้า `evidence/<api>-evidence.md` เป็น EV-nn ถ้า AI อ่านแล้วไม่เห็นโค้ดหรือเห็นแต่ผล ให้ถามผู้ใช้ก่อนใช้ผลปิดข้อ "ไม่มี"
12. คำสั่งที่ใช้ดึงนิยามต้องไม่ตัดกลางนิยาม: ใช้ `sed -n 'a,bp'` หรือ `grep -A` ที่ใหญ่พอ และเมื่อผลลัพธ์ลงท้ายกลางนิยาม (เช่น อาร์เรย์ที่ยังไม่ปิด `}`) ให้ถือว่าถูกตัดและออกสคริปต์ใหม่ ห้ามอนุมานส่วนที่เหลือเป็น [VER]
13. ข้อความ hint/error ทางการของ IDF (เช่น `components/esp_rom/hints.yml`) ใช้เป็นหลักฐานระดับ [VER] ว่าชื่อเก่าถูกเปลี่ยนเป็นอะไร ก่อนจะสรุปว่าชื่อเก่า "ถูกลบ" ให้ตรวจ hint ก่อน
14. การตรวจว่า symbol ถูก deprecated ต้อง grep คำว่า `deprecated` แบบกว้าง ห้ามค้นเฉพาะ `__attribute__((deprecated` เพราะ IDF ใช้ `_Pragma("GCC warning \"... is deprecated\"")` ด้วย (ตัวอย่าง `ESP_PD_DOMAIN_RTC8M` ใน `esp_sleep.h`) และบางจุดมีแค่หมายเหตุ "will be deprecated" ที่ยังไม่มี attribute (ตัวอย่าง `esp_sleep_enable_ext1_wakeup`) ให้แยกสามระดับในเอกสาร: มี attribute/pragma, มีแค่หมายเหตุ, ไม่มีเลย
15. ผลว่างจาก path หรือชื่อที่ AI เดา ไม่ใช่หลักฐานว่า "ไม่มี" (ตัวอย่าง: Y7 ใน `verify_gpio_unv4.sh` ค้นผิดไดเรกทอรี, Z3 ใน `verify_gpio_unv5.sh` เดาชื่อฟังก์ชันผิด) สคริปต์ต้องหาไฟล์ด้วย `find` ก่อนแล้วค่อย `-exec grep {} +` (ไม่ใช้ `grep $(find ...)` เพราะถ้า find ไม่พบ grep จะค้างรอ stdin) ถ้าไม่แน่ใจชื่อฟังก์ชัน ให้ค้นด้วยคำกว้าง (เช่น `grep -n -i hold`) แทนการเดาชื่อเต็ม และห้ามเขียนข้อความตัดสินผลไว้ท้ายหัวข้อ เช่น "ไม่มีบรรทัด = ไม่พบ" ให้เขียนแค่ `(จบ Xn)` แล้วตีความจากผลจริง
16. ก่อนสรุปว่า "ข้อความนี้ไม่มีใน IDF" ต้องค้นทั้ง header (`components/**/include`), ซอร์ส (`.c`) และเอกสาร (`docs/en/**/*.rst`) ของต้นไม้ v6.1 การค้นเฉพาะ header แล้วสรุปว่าไม่พบ ผิดได้ (ตัวอย่าง: เงื่อนไข "3 รอบ RTC slow clock" ของ GPIO wakeup อยู่ใน `sleep_modes.rst` ไม่อยู่ใน `esp_sleep.h`) ผลจาก docs ใน tree ที่ผู้ใช้รัน grep ถือเป็นหลักฐานระดับ [VER] และต้องระบุว่ามาจาก docs
17. เมื่อสรุปว่าโค้ดสาขา `#if/#else` ใดทำงานบน S3 ต้องมีหลักฐาน 2 ส่วนคือ (ก) ผล grep ของ macro เงื่อนไขใน `soc_caps.h` ของ S3 และ (ข) ระบุไดเรกทอรีที่ค้น ถ้าค้นแคบกว่าทั้ง `components/` ให้เขียนข้อจำกัดนั้นกำกับไว้ใน evidence ห้ามใช้ผลว่างอย่างเดียวฟันธง และเอกสารใน `docs/` ที่มี `.. only::` นำหน้า ต้องดูเงื่อนไขชิปของบล็อกนั้นก่อนใช้ (ตัวอย่าง: บรรทัด 616 ของ `sleep_modes.rst` พูดถึง "GPIO0 ~ 5" ซึ่งอยู่ใต้ `.. only:: esp32c2 or esp32c3` ไม่ใช่ S3)
18. การเลือกไฟล์ของ S3 ด้วย `find -path` ต้องใช้ `'*/esp32s3/*'` ห้ามใช้ `'*esp32s3*'` เพราะตรงกับ `esp32s31` ด้วย (ตัวอย่าง: Z2 และ Z17 ใน `verify_gpio_unv5.sh` / `verify_gpio_unv7.sh` ได้ผลปนกันสองชิป) เมื่อ evidence มีผลของชิปอื่นปน ให้ตัดทิ้งและบันทึกไว้ในหมายเหตุของ EV นั้น
19. กลไกที่ถูกอนุมานจากโค้ดฝั่งเดียว ต้องตรวจเงื่อนไขข้าม (skip/guard) ทุกจุดก่อนเขียนเป็นข้อกับดัก (ตัวอย่าง: GPIO-33 ถูกเขียนก่อนตรวจว่า `esp_gpio_is_reserved` ทำให้ขาถูกข้ามการ isolate) ถ้ายังตรวจไม่ครบ ให้เขียนคำแนะนำที่ปลอดภัยในทุกกรณีเป็นข้อหลัก และเขียนกลไกเป็นเงื่อนไขพร้อมป้าย [UNV]

### B.6 รูปแบบ Edit Block (แก้ไขแบบตัดแปะ)

AI ต้องใช้รูปแบบนี้ทุกครั้งที่แก้ไฟล์ที่มีอยู่แล้ว โดยไม่ให้ผู้ใช้ค้นตำแหน่งเอง

````markdown
### EDIT <ลำดับ> — ไฟล์: <path> — เวอร์ชันฐาน: <ver> → <ver ใหม่>
**ตำแหน่ง:** หัวข้อ "<ข้อความหัวข้อ>" · บรรทัดที่ขึ้นต้นด้วย `<ข้อความต้นบรรทัดแรกของบล็อกเดิม>`
**การกระทำ:** REPLACE | INSERT-AFTER | INSERT-BEFORE | DELETE

**ของเดิม** (ต้องตรงทุกตัวอักษร ใช้ค้นหา):
<บล็อกเดิม ครบทุกบรรทัดที่จะถูกแทนที่>

**ของใหม่:**
<บล็อกใหม่ครบถ้วน>
````

กฎ:
- ของเดิมต้องยาวพอให้ค้นเจอแบบไม่ซ้ำกันในไฟล์ (อย่างน้อย 2 บรรทัดเมื่อบรรทัดเดียวอาจซ้ำ)
- INSERT-AFTER/BEFORE ต้องระบุบล็อกอ้างอิงเต็ม
- ห้ามใช้คำว่า "ประมาณ", "ทำนองนี้", "..." ในบล็อกเดิมหรือใหม่
- ถ้าแก้เกิน 5 จุดในไฟล์เดียว หรือเกินประมาณ 30% ของไฟล์ ให้ออกไฟล์ใหม่ทั้งไฟล์แทน (จุดแก้ที่เป็นบรรทัดเดียวและไม่ซ้ำกันนับเป็น 1 จุดเล็ก)
- ทุก edit ต้องมีบรรทัดเวอร์ชันฐาน ถ้าผู้ใช้มีเวอร์ชันอื่น ให้แจ้งก่อนแก้
- หลังชุด edit ให้ AI สรุป "ผลที่ควรเห็น" 1–3 ข้อ เพื่อให้มนุษย์ตรวจว่าวางถูก
